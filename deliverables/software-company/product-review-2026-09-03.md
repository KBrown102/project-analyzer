# 项目结构分析器 1.0.0 — 产品方向评审报告

> 评审人：产品经理 许清楚（Xu）　|　评审日期：2026-09-03　|　性质：纯评审，不改代码
> 评审对象：`project-analyzer.html`（单文件零依赖 HTML 工具）+ Electron 打包副本

---

## 结论先行（TL;DR）

这是一个**定位精准、差异点真实、但天花板可见**的工具。

- **做对了的事**：把"项目结构体检"这件本该是 CLI/服务端专家的活，降维成了"拖文件夹、看图、勾选、导出提示词"的图形化操作，精准命中独立开发者/半吊子程序员这群被现有工具忽视的人。18 套模板 + 阶段制 + P0-P3 建议的"诊断—开方"闭环，市面上没有第二个工具这么干。
- **核心风险**：它是典型的"看一眼就用完"工具——**留存钩子几乎为零**。没有历史对比、没有回归拦截、没有持续价值。一次诊断之后，用户没有理由再回来。
- **最大短板**：模板硬编码、无自定义规则、无 CI/IDE 集成、导出格式单一（仅 Markdown 提示词）。这决定了它只能停留在"个人小工具"，难以走向团队/组织级。
- **一句话建议**：先别急着加模板，先把"可留存"做出来——历史快照 + 趋势对比 + JSON 导出，是从"一次性玩具"变成"反复回来的诊断仪"的最小跃迁。

## 一、产品定位与目标用户

### 1.1 解决什么痛点

| 痛点 | 现有方案的不足 | 本工具的解法 |
|---|---|---|
| "我这个项目到底缺什么？" | SonarQube 太重、要服务器；linters 只管结构不管流程完整性 | 拖进来 → 自动匹配模板 → 列出缺的阶段/产物/建议 |
| "我不知道项目走到哪一步了" | 没有工具按"生命周期阶段"判断进度 | 阶段进度条（lastDone→cur），直说"卡在系统设计" |
| "AI 能帮我补，但我不知道怎么描述现状" | Repomix 把整个仓库塞给 AI，token 爆炸；手写描述写不全 | 导出结构化提示词，只带勾选的缺口，省 token 又精准 |
| "我不想装环境、不想敲命令" | Yeoman/cookiecutter/linters 全是 CLI | 双击 HTML，零安装零依赖零联网 |

痛点抓得准。这四条是真实存在的、且现有工具确实没同时解决好的。

### 1.2 目标用户

明确是**独立开发者 / 半吊子程序员**，特征：偏好图形界面、排斥 CLI、喜欢"一键看结果"。补充判断：

- **游戏独立开发者**（尤其是用 Godot/Unity/LÖVE 的）——18 套模板里 game 占据最完整的 8 阶段流程（CCGS 八阶段），且 README 多处用游戏术语，说明这群人是**首批种子用户**。
- **接手陌生项目的人**——"项目介绍"自动从 README/package.json/title 推断，说明设计者考虑了"快速理解一个陌生项目"的场景。
- **给 AI 喂上下文的人**——提示词导出是核心卖点之一。

### 1.3 使用门槛评估

| 维度 | 评分 | 说明 |
|---|---|---|
| 安装门槛 | ★★★★★ | 双击 HTML 即用，Electron exe 拷给别人也能跑。这是最大优势。 |
| 操作门槛 | ★★★★☆ | 拖文件夹 → 看图。比 CLI（Yoeman/folderslint）低一个数量级。扣分：浏览器版选大目录会卡，README 自己也承认。 |
| 理解门槛 | ★★★☆☆ | 阶段进度、产物清单、P0-P3 对懂行的人直观；但对"半吊子"用户，"阶段制""产物""neg 语义"这些概念仍有学习成本。报告没有给"新手解释层"。 |
| 信任门槛 | ★★★★★ | 全程本地、零网络请求（README 反复强调、测试也验证），隐私故事满分。 |

**结论**：门槛在同类工具里最低档，是核心竞争力。但"看懂报告"这层对目标用户仍偏高——工具假定用户理解"阶段制流程"，而真正半吊子的人可能连"为什么要写 GDD"都不清楚。

## 二、功能完整性

### 2.1 18 套模板覆盖度

实际盘点（读源码 `PROFILES` + `PROFILE_ORDER`）：

| 分类 | 模板 | 阶段数 | 评价 |
|---|---|---|---|
| 通用基础 | generic / tool / lib / mini / meta | 3-5 | 基本盘覆盖，合理 |
| Web/服务 | web / server / microservice | 5-8 | web 与 server 拆分清晰，microservice 独立成套是亮点 |
| 垂直领域 | game / iac / embedded / extension / data / cli / mobile / desktop / aiml / devops | 6-8 | 覆盖面在同类工具里**最广** |

**覆盖够不够？** 对独立开发者场景，够。但有几个缺口：

- **缺 monorepo / 前端组件库专用模板**——microservice 偏后端，前端 monorepo（Nx/Turborepo）的结构健康度判断是空白。
- **缺"教学/示例项目"模板**——这类项目本就不需要全套工程化，目前会落进 generic 被误报一堆缺口。mini 模板只认 index.html 的小游戏，覆盖不到。
- **缺"配置/脚手架仓库"模板**——meta 模板勉强能用，但 meta 的判断条件（md 占比>35%）会把真正的配置仓库漏掉。

### 2.2 输出报告可操作性

报告结构（读源码 `renderCard` / `genPrompt`）：

```
项目介绍（自动推断） → 阶段进度条 → 产物齐全度清单 → 工程化信号（CI/测试/README）→ 缺口列表 → P0-P3 建议（带勾选）→ 提示词导出
```

**可操作性强的点**：
- 每条建议都带"该做什么（具体文件路径+内容方向）"+"为什么"，不是空话。
- 提示词导出按勾选项裁剪，五段式结构（概况/进度/产物表/缺口分组/给AI的指令），可直接粘给 AI。
- 阶段进度条带 evidence（证据路径），hover 可看，可追溯。

**可操作性不足的点**：
- **建议是"补什么"，不是"怎么补"**——detail 里写的是"README.md：一句话定位+怎么跑+目录说明"，但不会给你草稿。虽然提示词导出里要求 AI 给草稿，但工具自身不给。对真新手，"补 GDD"三个字可能还是不知道动笔。
- **无优先级总量控制**——一个差项目可能爆出十几条 P0/P1，没有"先做这 3 条"的聚焦。用户会被淹没。
- **建议准确度依赖正则匹配**——`/gdd/i` 命中就说"GDD 有"，但文件可能是空的或文不对题。工具只验"存在"，不验"质量"。这会制造**虚假安全感**（"我阶段都满了，应该没问题"），是产品层面的隐患。

### 2.3 明显缺失的功能

| 缺失功能 | 严重度 | 说明 |
|---|---|---|
| **历史对比/趋势** | 🔴 高 | 没法看"上次 3/8 阶段，这次 6/8"——这是留存的核心，见第四节 |
| **JSON/数据导出** | 🔴 高 | 只有 Markdown 提示词。无法被脚本/CI/其他工具消费，自我封闭 |
| **PDF 导出** | 🟡 中 | 给非技术人（老板/客户）看的报告，目前只有 Markdown |
| **忽略规则配置** | 🟡 中 | 噪音目录硬编码（28 个），用户无法加自己的（如 `vendor/`、`third_party/`） |
| **多项目批量** | 🟡 中 | 只能单个或双项目对比，无法一次体检 10 个微服务 |
| **自定义模板/规则** | 🟡 中 | 18 套写死，团队规范无法注入。限制了组织级扩展 |
| **依赖/架构分析** | 🟢 低 | 这不是它的定位（那是 ReposLens/NDepend 的活），但用户可能期待 |
| **跨平台** | 🟢 低 | README 写明 Windows。Mac/Linux 只能用浏览器版（exe 打包仅 Windows） |

## 三、竞品对比

### 3.1 竞品全景

调研了 6 类共 10+ 个工具，按"是否分析现有项目结构"分两阵营：

| 阵营 | 工具 | 做什么 | 和本工具的关系 |
|---|---|---|---|
| **脚手架（造项目）** | Yeoman、Cookiecutter | 从模板生成新项目骨架 | **反向**——它们造，本工具查。互补非竞争 |
| **结构 lint（卡规则）** | folderslint、project-structure-lint、eslint-plugin-project-structure、structlint | 配置规则 → CI 里 fail/ pass | **同向不同层**——它们"卡底线"，本工具"开处方"。它们要配置+CLI，本工具零配置+GUI |
| **代码质量（查缺陷）** | SonarQube、Semgrep | 静态分析 bug/漏洞/坏味道，30+ 语言 | **不同层**——它们查代码内部，本工具查项目骨架。完全互补 |
| **架构分析（查耦合）** | ReposLens、NDepend | 模块依赖图、循环依赖、耦合度 | **不同层**——它们查架构健康，本工具查文件齐全度 |
| **仓库打包（喂 AI）** | Repomix | 整仓打成单文件喂 LLM，带 token 计数+密钥扫描 | **同方向不同策略**——Repomix"全给"，本工具"只给诊断+缺口"。本工具更省 token |
| **IDE 结构文档** | VS Code: Project Analyzer、RepoInsight、Explain This Project | 生成 PROJECT_OVERVIEW.md，部分带 AI 摘要+git 洞察 | **最近竞品**——同样"解释这是什么项目"。但它们输出文档，本工具输出"诊断+处方" |

### 3.3 差异化与 USP

本工具的**独特价值（USP）** 是三件事的组合，没有任何单一竞品同时具备：

1. **"诊断—开方"闭环**：不只是说"缺 README"（linters 也做），而是告诉你"你卡在系统设计阶段，该补 design/gdd/00-overview.md，为什么补、优先级 P1"——把结构检查升级成了流程成熟度咨询。
2. **可裁剪的 AI 提示词导出**：勾选哪些缺口就只导出哪些，五段式结构化喂给 AI。比 Repomix 的"全量打包"省 token、比手写描述更全。这是当前 AI 编程浪潮下的精准切入点。
3. **零门槛零隐私**：双击 HTML、全程本地。在这个领域， SonarQube 要服务器、linters 要 CLI、ReposLens 要 GitHub 授权——本工具是唯一"给怕命令行的人用的结构体检仪"。

**但 USP 的脆弱性**：这三点都不构成护城河。阶段制模板是经验沉淀、可被复制；提示词导出是好 UX、可被模仿；零安装是 HTML 天然属性、无技术壁垒。真正的壁垒只能来自**网络效应/数据沉淀**（模板社区、历史趋势），而这恰是目前完全缺失的。

## 四、用户价值评估

### 4.1 对独立开发者/小团队的真实价值

**价值是真实的，但偏"一次性"。**

- **首次使用价值高**：一个混乱的项目拖进来，立刻看到"缺 7 个产物、卡在第 2 阶段、3 条 P0"，这种"顿悟时刻"很有冲击力。对从没做过结构自检的人，值回票价。
- **重复使用价值低**：诊断完、补完缺口之后呢？没有"再测一次看进步"的钩子（无历史），没有"别让它退步"的钩子（无 CI），没有"换模板试试"的钩子（模板写死）。用户补完缺口就走了，**没有理由回来**。
- **对团队价值更低**：团队需要的是"统一标准+持续保障"，本工具给不了自定义规则和 CI 集成。一个人用着爽，推广给团队会卡在"我们公司的规范和你的 18 套模板对不上"。

### 4.2 留存钩子诊断

| 留存机制 | 现状 | 影响 |
|---|---|---|
| 历史快照/趋势 | ❌ 无 | 致命——无法体现"工具帮我进步了"，无成就感闭环 |
| 回归拦截(CI) | ❌ 无 | 致命——补完的缺口下次又会缺，工具管不着 |
| 自定义模板 | ❌ 无 | 限制——团队用不上自己的标准就不会沉淀 |
| 定期复检提醒 | ❌ 无 | 缺失——没有"项目又长歪了，回来看一眼"的召回 |
| 模板市场/社区 | ❌ 无 | 缺失——无 UGC 内容生态 |
| 对比模式 | ✅ 有(双项目) | 唯一可重复使用的场景，但场景窄（只在迁移/重构时用） |

**结论**：目前是"看一眼就用完"的工具。要变成"会反复回来用"，**至少需要历史快照**——这是第一优先级，见第五节。

## 五、Roadmap 建议（优先级排序）

> 原则：先做"可留存"，再做"可扩展"，最后做"可规模化"。不要先加模板（边际效益递减）。

### P0 — 历史快照 + 趋势对比（预期收益：高 / 难度：低）

**做什么**：每次分析自动存一份快照（localStorage 或导出 .json），支持"对比上次"——上次 3/8 阶段，这次 6/8，新增补了 GDD、CI。可视化成进步曲线。

**为什么排第一**：这是从"一次性玩具"到"反复回来的诊断仪"的唯一跃迁点。没有它，留存永远是零。技术上极轻（数据结构 `buildData` 已经现成，序列化成 JSON 存 localStorage 即可）。

**预期收益**：留存率显著提升；用户有"工具帮我变好"的成就感闭环；产生"值得付费/分享"的动机。

### P1 — JSON 数据导出 + CI 集成入口（预期收益：高 / 难度：中）

**做什么**：
1. 报告可导出为 JSON（结构化数据，而非只有 Markdown 提示词）。
2. 提供一个 headless 模式（CLI 或 `--json` 参数），让 CI 能跑它、用 exit code 卡"P0 缺口数>0 就 fail"。

**为什么排第二**：JSON 导出打开"可被消费"的口子——其他工具、脚本、看板都能用你的诊断结果。CI 集成则补上"回归拦截"这个致命缺口。两者是同一件事的两面（数据出来 → 才能在流水线里用）。

**预期收益**：从个人工具走向团队工具的第一步；出现"团队规范校验"的使用场景；为自定义规则铺路。

**难度提示**：Electron 版加 `--json` 容易；纯 HTML 版做 CI 集成需要把核心逻辑抽成可独立运行的 JS 模块（目前逻辑在 `<script>` 里，测试已用 vm harness 抽出，复用性好）。

### P2 — 自定义模板 / 规则配置（预期收益：中高 / 难度：中）

**做什么**：允许用户加载自己的模板定义（JSON/YAML），覆盖或新增 18 套内置模板。至少支持：自定义 phases / artifacts / advice 规则、自定义噪音目录。

**为什么排第三**：这是"可扩展"的钥匙。团队有了自己的规范才能沉淀、才会持续用。但不排在前面是因为——对独立开发者（当前核心用户），自定义需求没那么强；且没有历史/CI 的留存基础，自定义模板也留不住人。

**预期收益**：解锁团队市场；为模板市场（UGC）埋下种子；降低"18 套不够用"的覆盖焦虑。

### P3 — 导出格式补全：PDF + 可分享链接（预期收益：中 / 难度：低-中）

**做什么**：报告可导出 PDF（给非技术干系人）；可选生成一个纯静态的可分享 HTML 报告（脱敏后可发给别人看，不含源码路径敏感信息）。

**为什么排第四**：Markdown 提示词是给 AI 的，PDF/HTML 是给人的。补全后报告能流向更多场景（汇报、外包交接、开源项目 README 附录）。但优先级低于留存和扩展。

### P4 — 模板市场 / 社区生态（预期收益：高但远期 / 难度：高）

**做什么**：用户上传/分享模板包，社区评分，热门模板一键安装。类似 Yeoman generator 生态但更轻。

**为什么排最后**：这是终局愿景（网络效应=护城河），但前置依赖太多——得先有自定义模板（P2）、有用户基数、有质量审核机制。现在做是空中楼阁。列为北极星方向，不急于当下。

## 六、风险提示

1. **虚假安全感风险**：工具只验"文件存在"不验"内容质量"，可能让用户误以为"阶段满了=项目健康"。建议在报告里加质量提示（如"GDD 文件 <100 字，可能只是占位"）。
2. **正则误判风险**：阶段/产物判断全靠正则匹配路径，易被巧合命名欺骗。变异测试已覆盖 5 处，但 18 套 × 数十正则的交叉面仍大。建议加"置信度"标注。
3. **单文件架构的扩展瓶颈**：131KB 单 HTML，逻辑全在一个 `<script>`。加自定义模板、CI、历史等功能后可维护性会下降。建议在 P1/P2 阶段评估是否拆模块（测试 harness 已证明逻辑可独立抽出）。
